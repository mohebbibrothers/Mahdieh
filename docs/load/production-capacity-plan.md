# برنامهٔ ظرفیت تولید — عدد واقعی را کجا و چطور بگیریم

> این سند، **دستور کار** است، نه گزارش. گزارشِ اندازه‌گیری‌های موجود در
> `docs/load/2026-10-16-load-64u-capacity.md` است. تفاوت مهم است: آن یکی می‌گوید
> «روی این ماشین چه دیدیم»، این یکی می‌گوید «روی سرور واقعی چه باید ببینیم و
> چه عددی قبول است».

## چرا اندازه‌گیری روی سرور واقعی، پیش از بازکردن لازم است؟

مدل ما بر پایهٔ بارسنجی روی میزبان **۲ هستهٔ مشترک** ساخته شده (میانهٔ چند پاس):

| کارگر | p95 در ۶۴ کاربر | نتیجه |
| --- | --- | --- |
| `-k sync -w 5` | **۱۲۹۲ ms** | انتخاب شد (ADR-0015) |
| `uvicorn-worker` | ۱۸۹۰ ms | رد شد |
| `-k gthread` | ۲۱۰۹ ms | رد شد |

برآورد قانون لیتل: هر درخواست ≈ ۳۵ میلی‌ثانیه CPU ⇒ روی ۴ هستهٔ اختصاصی
≈ ۱۱۴ rps، معادل ≈ ۹۱ کاربرِ هم‌زمانِ فعال. عددِ **واقعی** باید روی سرور تولید
تأیید شود، چون میزبان مشترک، نویز همسایه و نوع CPU اثر جدی دارند.

## معیار پذیرش (پیش از بازکردن سایت)

| سنجه | آستانه | اگر رد شد |
| --- | --- | --- |
| p95 زمان پاسخ، ۶۴ کاربر هم‌زمان | **≤ ۸۰۰ ms** | `WEB_CONCURRENCY` را بالا ببرید؛ اگر نشد، سد را بررسی کنید |
| نرخ ۵xx | **۰** | لاگ `django.request`؛ اگر ۵۰۳ بود، سدِ لبه زودتر از موعد فعال شده |
| تعداد پاسخ ۵۰۳ از سد | **۰** در ۶۴ کاربر | سقف `limit_conn`/`WEB_CONCURRENCY` ناهمخوان است |
| حافظهٔ اوج | < ۷۰٪ RAM | کاهش کارگر یا بررسی نشت |
| سلامت در پایان آزمون | `healthy` | هر بار |

## اجرای آزمون (روی سرور، ۱۰ دقیقه)

```bash
# ۱) سرویس در حالت تولید بالا باشد و پایش سبز
sudo systemctl status mahdieh --no-pager
python manage.py healthcheck --base-url http://127.0.0.1:8000 --behind-proxy

# ۲) آزمون، سه پاس پیاپی (میانهٔ سه پاس، نه یک پاس)
cd /srv/mahdieh
.venv/bin/python scripts/load_test.py --users 64 --duration 120 --server-cpus 4 --repeats 3 \
  --base-url http://127.0.0.1:8000

# ۳) همان آزمون با ۹۶ کاربر (سقف عملی) — برای دیدن «کجا می‌شکند»
.venv/bin/python scripts/load_test.py --users 96 --duration 120 --server-cpus 4 --repeats 2 \
  --base-url http://127.0.0.1:8000
```

ابزار در پایان، جدول p50/p95/p99، نرخ خطا و محدودیت را چاپ می‌کند و اگر
`p95 > 800ms` یا هر ۵xx ببیند، **کد خروج ۱** می‌دهد (یعنی خودش هم گیت است).

## چند تصمیم وابسته

- **`WEB_CONCURRENCY`:** قاعدهٔ ساده: یک کارگر به‌ازای هر هسته، حداقل ۳. با ۴
  هسته: `WEB_CONCURRENCY=4`. اگر p95 بالاتر از آستانه بود، نخست **کندی کوئری**
  را ببینید، نه افزایش کورکورانهٔ کارگر (حافظه و اتصال پایگاه‌داده محدود است).
- **`DATABASE_POOL_MAX_SIZE`:** قاعدهٔ ثابت پروژه:
  `WEB_CONCURRENCY × DATABASE_POOL_MAX_SIZE ≤ max_connections − ۱۰`
  (در `.env.example` هم نوشته شده).
- **`LOAD_SHEDDING_WSGI_ENABLED`:** با کارگر `sync` خاموش می‌ماند؛ سدِ واقعی
  Nginx است (ADR-0016). فقط با کارگرِ رشته‌ای روشن کنید.
- **بازهٔ بازبینی:** بارسنجی را پس از هر تغییر بزرگ (قالب صفحهٔ اصلی، گزارش
  اکسل، سیاست جدید) یک بار سبک تکرار کنید.

## حداقلِ لازم برای «سندِ ظرفیتِ کامل»

۱. میزبان واقعی مستند شود (CPU/RAM/دیسک).
۲. سه پاس ۶۴ کاربر و دو پاس ۹۶ کاربر ثبت شود.
۳. عدد `WEB_CONCURRENCY` و اندازهٔ استخر پایگاه‌داده در همان سند بیاید.
۴. اگر آستانه رد شد، تصمیم اصلاحی هم نوشته شود (نه فقط عدد).
