# قرارداد API مهدیه — راهنمای تیم فرانت‌اند

این سند برای **تیم فرانت** نوشته شده است: بک‌اند شرکت را ما می‌سازیم و فرانت کار
جدا دارد. پس قاعدهٔ حاکم این است: «آنچه در سند نیست، وجود ندارد.» اگر نقطهٔ
پایانی در `docs/api/openapi.yaml` نباشد یا شکل بدنه/پاسخش مشخص نباشد، فرانت
نمی‌تواند مطمئن روی آن بسازد — و آزمون‌های ما همان شکاف را قرمز می‌کنند.

---

## ۱) منابع قرارداد

| منبع | آدرس / مسیر | توضیح |
| --- | --- | --- |
| سند OpenAPI | `docs/api/openapi.yaml` | **منبع حقیقت** برای تولید کلاینت تایپ‌دار |
| بازتولید سند | `make schema` | بی‌هشدار و بارزسی‌شده (`--validate --fail-on-warn`) |
| نمایش تعاملی | `/api/docs/` | Swagger UI روی همان سند |
| سند خام | `/api/schema/` | YAML؛ همان چیزی که در مخزن است |
| آزمون نگهبان | `src/tests/test_api_contract.py` | ۸ آزمون: پوشش، شکل، یکتایی `operationId`، ناهم‌خوانی سند |

اگر سند و کد از هم جدا شوند، `test_committed_schema_matches_fresh_generation`
قرمز می‌شود؛ یعنی فرانت هرگز سند کهنه نمی‌گیرد.

## ۲) آدرس پایه و نسخه‌بندی

- همهٔ مسیرها زیر `/api/v1/` هستند (بدون اسلش پایانی).
- `GET /api/v1/meta` نسخهٔ قرارداد را می‌دهد: `schema_version: "v1"` به‌همراه محیط،
  منطقهٔ زمانی و امروزِ جلالی.
- تغییر **شکننده** ⇒ نسخهٔ تازه (`/api/v2/`) و اعلام `Deprecation`/`Sunset` بر پایهٔ
  RFC 8594. تغییر غیرشکننده (افزودن کلید) بدون نسخهٔ تازه انجام می‌شود.
- قاعده برای فرانت: کلیدهای **ناشناخته را نادیده بگیرید**، روی حضور قطعی یک کلید
  تازه حساب نکنید.

## ۳) احراز هویت (بدون ایمیل، بدون رمز)

1. `POST /api/v1/auth/otp/request` با `{"phone": "09xxxxxxxxx"}` ⇒ `202`، ارسال کد
   پیامکی. پاسخ برای شمارهٔ ثبت‌شده و ثبت‌نشده **یکسان** است (ضد شمارش کاربران).
2. `POST /api/v1/auth/otp/verify` با `{"phone": …, "code": …}` ⇒ `200` و کوکی نشست.
3. `GET /api/v1/me` ⇒ پروفایل؛ `PATCH /api/v1/me/profile` ⇒ تکمیل پروفایل
   (نام، نام خانوادگی، ملیت، شهر؛ اتباع ایران: استان + کد ملی؛ زائر خارجی:
   گذرنامه — ADR-0019). همهٔ خطاهای فرم یک‌جا در `errors` برمی‌گردند.
4. `POST /api/v1/auth/logout` ⇒ `204`؛ `POST /api/v1/auth/logout-all` ⇒ خروج از همهٔ
   دستگاه‌ها؛ `GET /api/v1/me/sessions` و `POST …/me/sessions/{id}/revoke`.
5. **کارکنان (ADR-0018):** پس از OTP، تا تأیید TOTP هر مسیر کارکنان `403 mfa_required`
   می‌دهد (بدنه کلید `mfa` با `enrolled`/`verified` دارد). مسیرها:
   `GET auth/mfa/status` • `POST auth/mfa/totp/setup` (QR SVG + راز) •
   `POST auth/mfa/totp/confirm {code}` (۱۰ کد بازیابی، فقط همین یک‌بار) •
   `POST auth/mfa/verify {code}` (TOTP یا کد بازیابی). کارهای پرخطر اگر تأیید از
   ۱۰ دقیقه کهنه‌تر باشد `403 step_up_required` می‌دهند ⇒ فرانت مودال کد را باز
   می‌کند، `verify` می‌زند و همان درخواست را تکرار می‌کند.

نکته‌های عملی برای فرانت:

- نشست **کوکی‌محور** است؛ برای درخواست‌های نوشتنی (`POST/PATCH/DELETE`) باید هدر
  `X-CSRFToken` از کوکی `csrftoken` فرستاده شود (`credentials: "include"` در fetch).
- `GET /api/v1/auth/csrf` کوکی `csrftoken` را می‌کارد (بی‌کش) — فرانت پیش از نخستین
  نوشتن یک‌بار صدا بزند.
- **چیدمان تولید هم‌مبدأ است (ADR-0017):** Next و API زیر یک دامنه پشت Nginx
  (`deploy/nginx/mahdieh-split.conf`)؛ CORS لازم نیست. ابزار
  `MAHDIEH_CORS_ORIGINS` فقط برای سناریوی دامنهٔ جدا (مثلاً پیش‌نمایش) باقی است.
- سقف نرخ ورود: `otp/request` پنج بار در دقیقه، `otp/verify` ده بار در دقیقه
  (به‌ازای هر IP/کاربر). عبور از سقف ⇒ `429` با هدر `Retry-After`.

## ۴) قرارداد خطا (RFC 9457)

همهٔ خطاها `application/problem+json` با این شکل هستند:

```json
{
  "type": "https://docs.mahdieh.ir/problems/slot_taken",
  "title": "تصادم با وضعیت موجود",
  "status": 409,
  "detail": "این سانس همین حالا توسط زائر دیگری گرفته شد.",
  "code": "slot_taken",
  "instance": "/api/v1/reservations",
  "trace_id": "01HQ2Z4N6T9K8M7P5R3S1V0X2Y",
  "errors": { "guests_count": ["حداکثر ظرفیت این واحد ۶ نفر است."] }
}
```

- `code` کلید ماشینیِ پایدار است — فرانت **روی `code`** شرط بگذارد، نه روی `detail`
  فارسی. فهرست کدها در بخش `schemas/Problem` سند و در خودِ کد موجود است
  (نمونه‌ها: `slot_taken`, `validation_error`, `offer_expired`, `rate_limited`,
  `not_owner`, `period_over`).
- `trace_id` را در گزارش خطای خود نگه دارید؛ پشتیبانی با همان پیگیری می‌کند.
- نگاشت وضعیت‌ها (ADR-0017): `400` فقط بدنهٔ بدشکل (JSON خراب) • `401` ورود لازم •
  `403` بی‌مجوز (`mfa_required`/`step_up_required` برای کارکنان) • `404` نبود **یا
  مال شما نیست** • `409` تصادم/وضعیت ناسازگار • `410` پیوند منقضی/ابطال‌شده •
  `422` **هر** خطای اعتبارسنجی، همیشه با `errors` فیلدبه‌فیلد • `429` سقف نرخ (با
  `retry_after`) • `503` خارج از ظرفیت (با `Retry-After: 5`).
- خطاهای اعتبارسنجی **یک‌جا** برمی‌گردند (نه یکی‌یکی): فرم را با یک رفت‌وبرگشت کامل
  علامت بزنید. قواعد رزرو افزون بر آن `violations` و هنگام تصادم `alternatives` دارند.

## ۵) هم‌توانی (تکرار امن درخواست)

`POST /api/v1/reservations` هدر اختیاری `Idempotency-Key` را می‌پذیرد: اگر فرانت
شبکه را از دست بدهد و همان کلید را دوباره بفرستد، **دو رزرو ساخته نمی‌شود**؛ پاسخ
نخست بازپخش می‌شود. پیشنهاد ما: کلید یکتای هر تلاش کاربر (مثلاً UUID) را بسازید و
در تلاش‌های مجدد همان را نگه دارید.

## ۵.۵) اطلاعات تماس پذیرش و «مبدأ دقیق» — دو پرسش تکرارشوندهٔ تیم فرانت

### الف) نشانی/تلفن پذیرش

**این‌ها در پایگاه‌دادهٔ بک‌اند ذخیره نمی‌شوند.** دادهٔ کسب‌وکار نیستند؛ فرانت
می‌تواند نسخهٔ خودش را داشته باشد و هیچ‌چیز نمی‌شکند. ولی برای این‌که سه مصرف‌کننده
(صفحهٔ راهنما در همین مخزن، نمونه‌های SSR، و فرانت) **واگرا نشوند**، یک نسخهٔ
رسمی هم از بک‌اند منتشر می‌شود:

```jsonc
// GET /api/v1/meta
{
  "service": "mahdieh",
  "environment": "production",
  "schema_version": "v1",
  "today_jalali": "1405-07-24",
  "timezone": "Asia/Tehran",
  "contact": { "phone": "…", "address": "…" }   // اگر تنظیم نشده باشد: null
}
```

قرارداد کلید `contact`:

- `null` یعنی **بک‌اند نسخه‌ای منتشر نکرده** ⇒ فرانت نسخهٔ خودش را نشان دهد.
- هیچ‌وقت شماره یا نشانی «نمونه/ساختگی» از بک‌اند نمی‌آید.
- اگر فقط نشانی تنظیم شده باشد، `phone` رشتهٔ خالی می‌ماند؛ **دکمهٔ تماس را با
  شمارهٔ خالی نسازید** (`tel:` خالی، کاربر را به هیچ‌جا نمی‌برد).

### ب) «مبدأ دقیق فرانت» یعنی چه؟

مبدأ (origin) در مرورگر = **پروتکل + دامنه + پورت**؛ بدون مسیر و بدون اسلش پایانی.

| مثال | مبدأ؟ | چرا |
| --- | --- | --- |
| `https://mahdie-shohada.ir` | ✅ | پروتکل + دامنه |
| `https://www.mahdie-shohada.ir` | ✅ | دامنهٔ `www` **مبدأ جدا** است |
| `https://app.mahdie-shohada.ir` | ✅ | زیر‌دامنه هم مبدأ جداست |
| `http://localhost:5173` | ✅ | پورت هم بخشی از مبدأ است |
| `https://mahdie-shohada.ir/` | ❌ | اسلش پایانی؛ مبدأ «دکمهٔ کارنکردنی» می‌شود |
| `mahdie-shohada.ir` | ❌ | پروتکل ندارد |

سه حالت تصمیم:

1. **فرانت و بک‌اند یک دامنه‌اند** (پیشنهاد ما): `MAHDIEH_CORS_ORIGINS` را **خالی**
   بگذارید. خالی = بسته و امن؛ درخواست‌ها هم‌مبدأ‌اند و اصلاً CORS لازم نیست.
2. **فرانت زیر‌دامنهٔ دیگر است** (`app.example.com` ⇒ `api.example.com`): همان
   زیر‌دامنه را بنویسید. `MAHDIEH_CROSS_SITE_COOKIES=true` هم لازم می‌شود
   (کوکی بین‌دامنه) و **فقط روی HTTPS** معنا دارد.
3. **فرانت هنوز بالا نیست**: خالی بگذارید. روزی که دامنه مشخص شد، یک متغیر محیطی
   تغییر می‌کند؛ **هیچ تغییری در کد لازم نیست**. همین امروز هم می‌توانید بدون
   نگرانی کار کنید: برای توسعهٔ محلی، آدرس `http://localhost:<پورت>` را به
   همان متغیر بدهید (مثلاً `http://localhost:5173`).

> اگر مقدار اشتباه بدهید، سامانه **پیش از استقرار** قرمز می‌شود: سه سیستم‌چک
> `mahdieh.E001/E002/E003` قالب نادرست، مبدأ بیگانه در CSRF و کوکی ناامن را
> می‌گیرند (نگاه کنید به `docs/runbooks/deploy.md`).

## ۶) صفحه‌بندی، فیلتر و اندازهٔ پاسخ

**قاعدهٔ یک‌خطی:** فهرست‌های **رشدی** پوشش دارند، فهرست‌های **مرجع** آرایهٔ ساده‌اند.

| مسیر | شکل پاسخ | مرتب‌سازی |
| --- | --- | --- |
| `GET /api/v1/reservations` | `{results, meta}` + `meta.total` | `-created_at, -id` |
| `GET /api/v1/staff/reservations` | `{results, meta}` (بدون total) | `-created_at, -id` |
| `GET /api/v1/waitlist` | `{results, meta}` + `meta.total` | `-created_at, -id` |
| `api/v1/units`, `/property`, `/occasions`, `/calendar`, `/blocks` | آرایهٔ ساده | ثابت/محدود |

- `meta` = `{"next", "previous", "page_size"}` و در فهرست‌های کاربرمحور `total`.
  `total` روی میز کارکنان **عمداً نیست**: کوئری شمارش روی میز بزرگ گران است و
  ارزش عملیاتی‌اش کم.
- پیمایش: نشانیِ `meta.next` را همان‌طور که هست دنبال کنید؛ دستی `cursor` نسازید.
- `page_size` قابل تنظیم است با سقف سخت ۱۰۰ (میز کارکنان ۵۰).
- مکان‌نمای خراب ⇒ `404` با بدنهٔ `problem+json` — نه ۵۰۰ و نه صفحهٔ خالی.
- فیلتر دامنهٔ رزروهای من: `scope=upcoming|past|all`.

## ۷) زمان، تقویم و ارقام

- همهٔ زمان‌ها **ISO 8601 با منطقه‌زمانی** (`2026-10-20T08:00:00+03:30`)؛ ذخیره در
  UTC و نمایش محلی.
- «نیم‌روز» واحد اقامت است: **روز** ۰۸:۰۰–۲۰:۰۰ و **شب** ۲۰:۰۰–۰۸:۰۰.
  کمینهٔ اقامت یک نیم‌روز، بیشینهٔ پیش‌فرض یک هفته (۷ شبانه‌روز).
- هر رکورد، در کنار تاریخ میلادی، معادل جلالی هم دارد (`date_jalali`,
  `today_jalali`). **قرارداد ماشینی همیشه ارقام لاتین دارد**؛ فارسی‌سازی ارقام
  کار لایهٔ نمایش فرانت است (ADR-0014).

## ۹) گزارش‌ها و فایل‌ها

- `GET /api/v1/staff/reports/summary` ⇒ خلاصهٔ عددی (JSON).
- `GET /api/v1/staff/reports/reservations.xlsx?from&to&units&status&phones` ⇒ فایل اکسل
  (`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`). فرانت فقط
  لینک دانلود بسازد؛ پارس اکسل کار فرانت نیست.
  - `phones=masked` (پیش‌فرض) | `full` — `full` فقط مدیر با تأیید تازه
    (`403 manager_only` / `403 step_up_required`)؛ مقدار ناشناخته ⇒ `422 invalid_phones_mode`.
  - هدرها: `X-Report-SHA256`، `X-Report-Phones`، `Cache-Control: private, no-store`.
- `GET /api/v1/reservations/{code}/calendar.ics` و `GET /api/v1/me/calendar.ics` ⇒
  `text/calendar` برای افزودن به تقویم گوشی.

## ۱۱) چک‌لیست باقی‌ماندهٔ هماهنگی (بک‌اند ⇒ فرانت)

| مورد | وضعیت | توضیح |
| --- | --- | --- |
| سند OpenAPI کامل و بی‌هشدار | ✅ انجام شد | ۵۶ مسیر، ۶۱ عملیات؛ آزمون‌های نگهبان قرارداد |
| `GET /api/v1/meta` در سند | ✅ انجام شد | پیش‌تر تنها نقطهٔ غایب سند بود |

| فهرست مجاز CORS برای مبدأ فرانت | ✅ لازم نیست | چیدمان هم‌مبدأ (ADR-0017) |
| اتصال صفحه‌بندی مکان‌نمایی به فهرست‌ها | ✅ انجام شد | سه فهرست رشدی؛ فصل ۶ همین سند |
| API کامل فرانت مستقل | ✅ انجام شد | فصل ۱۰ همین سند؛ آزمون `test_frontend_api.py` |
| تأیید دومرحله‌ای کارکنان | ✅ انجام شد | ADR-0018؛ آزمون `test_staff_mfa.py` |
| نگهداری دادهٔ زائر (سیاست عمر) | ✅ انجام شد | `docs/product/data-retention.md` |
