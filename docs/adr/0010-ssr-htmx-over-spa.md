# ADR-0010: SSR + HTMX به‌جای SPA

**وضعیت:** پذیرفته · **تاریخ:** ۲۰۲۶-۱۰-۱۵

> **به‌روزرسانی ۱۴۰۵/۰۷/۲۵:** بخشی از این تصمیم با [ADR-0017](0017-same-origin-split-and-422-contract.md) جایگزین شد — فرانت عمومی و پنل کارکنان به Next.js (هم‌مبدأ) می‌روند؛ SSR جنگو به‌عنوان پشتیبانِ قطعی و تابلوی پذیرش باقی می‌ماند و API کامل همچنان قرارداد اصلی است.

## زمینه
اصل اول کارفرما: «کاربرپسند و آسان روی موبایل». کاربران غالباً با موبایل و اینترنت ضعیف وارد می‌شوند؛ تقویم رزرو باید سریع، در دسترس و قابل ایندکس باشد.

## تصمیم
صفحات با قالب‌های Django (SSR) + **HTMX** برای تعامل‌های جزئی + **Alpine.js** برای حالت محلی، با Tailwind و حروف‌چینی فارسی. API کامل DRF در موازات برای آیندهٔ اپلیکیشن موبایل.

## چرا
- **سرعت و SEO:** HTML آمادهٔ نمایش، بارگذاری اولیه سریع، صفحات قابل ایندکس.
- **سادگی عملیاتی:** بدون زنجیرهٔ ساخت پیچیدهٔ فرانت و وضعیت دوگانه.
- **تطبیق با مرورگرهای قدیمی‌تر:** HTMX به‌جای حجم سنگین JS.
- تجربهٔ بهتر در شبکهٔ ضعیف موبایل.

## پیامدها
- ✅ لمس‌های کمتر تا رزرو، سرعت بالا، نگه‌داری ساده
- ✅ یک زبان برای تمام لایه‌ها ⇒ توسعهٔ سریع‌تر و خطای کمتر
- ⚠️ تعامل‌های بسیار پویا (تابلوی ادمین) نیاز به JS هدفمند دارد
- ⚠️ تصمیم دربارهٔ PWA/آفلاین بعداً ارزیابی می‌شود (سرویس‌ورکر برای «رزروهای من»)
