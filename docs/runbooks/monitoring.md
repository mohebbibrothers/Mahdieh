# رانبوک پایش — «از کجا بفهمیم سایت خوابیده، پیش از آنکه زائر تلفن بزند»

> مخاطب: مهندس عملیات. این سند سه چیز دارد: **چه چیزی** پایش می‌شود، **کجا**
> هشدار می‌رود، و **چطور** مطمئن شویم خودِ پایشگر زنده است. آخرین بند (آزمون
> آژیر) مهم‌ترین بند است: پایشِ آزمایش‌نشده، اطمینانِ دروغ است.

---

## ۱) لایه‌های پایش و «کد خروجی» که معنا دارد

| لایه | ابزار | چه چیزی را می‌بیند |
| --- | --- | --- |
| زنده‌بودن فرآیند | `GET /health/live/` | کارگر پاسخ می‌دهد؟ (سبک، بدون وابستگی) |
| آمادگی | `GET /health/ready/` | پایگاه‌داده + کش + مهاجرت‌های اجرانشده |
| گزارش عملیاتی | `GET /health/detailed/` (کارکنان) | عمق صف Outbox، ذخیره‌سازی، وضعیت پیامک |
| **پایشگر دوره‌ای** | `manage.py healthcheck` + `mahdieh-healthcheck.timer` | جدا کردن «افت‌کرده» از «ناسالم» و **هشدار هنگام تغییر** |

قرارداد کد خروجی `healthcheck` (stable؛ روی آن حساب می‌کنیم):

| کد | معنا | کار درست | آستانهٔ واکنش |
| --- | --- | --- | --- |
| ۰ | سالم | هیچ | — |
| ۱ | افت‌کرده: کش یا ذخیره‌سازی | سر فرصت ببینید؛ **ترافیک بماند** | در ساعات کاری |
| ۲ | ناسالم: پایگاه‌داده یا مهاجرت معلق | همان لحظهٔ `incident-response.md` بخش ۳ | بی‌درنگ |

منطق تفکیک: کش منبع حقیقت نیست. اگر قطعیِ کش ترافیک را قطع کند، خودمان را
بی‌دلیل از چرخه بیرون گذاشته‌ایم. ولی «سکوت» هم گزینه نیست؛ پس افت‌کرده
گزارش می‌شود، تماس را قطع نمی‌کند، و پایشگر آن را به گوش تیم می‌رساند.

## ۲) هشدار: چرا هر ۵ دقیقه ایمیل نمی‌آید؟

پایشگری که اسپم بسازد، خیلی زود خفه می‌شود و دیگر کسی نگاهش نمی‌کند. پس:

| رخداد | ایمیل می‌رود؟ |
| --- | --- |
| نخستین بار که وضعیت بد می‌شود (تغییر) | ✅ یک ایمیل |
| تکرار همان وضعیت بد در اجرای بعدی | ❌ خیر |
| وضعیت بد **پایدار** (بیش از ۱۲ ساعت) | ✅ یک یادآوری دیرهنگام، بعد هر ۱۲ ساعت |
| بازگشت به سالم | ✅ یک ایمیل «بهبود» |

* گیرندگان: `MAHDIEH_ADMINS` (فهرست نشانی‌های ایمیل).
* قابل تنظیم: `--renotify-after` (ساعتِ فاصلهٔ یادآوری؛ `0` = هرگز یادآوری نکن).
* پروندهٔ وضعیت: `var/healthcheck.state` — وضعیت و زمان آخرین هشدار. **این پرونده
  را پاک نکنید**؛ با پاک‌شدنش، یادآوری‌ها از نو شروع می‌شود (اسپم).

```bash
# پایش دستی روی سرور (مسیر واقعی nginx → gunicorn)
python manage.py healthcheck --base-url http://127.0.0.1:8000 --behind-proxy --json

# سنجش بدون شبکه (مثلاً در CI یا هنگام عیب‌یابی درون‌فرآیندی)
python manage.py healthcheck --json

# فقط بررسی «چه زمانی آخرین بار پایش شد؟»
cat /srv/mahdieh/var/healthcheck.state
```

## ۳) زمان‌بند و اجرای خودکار

```bash
sudo cp deploy/systemd/mahdieh-healthcheck.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now mahdieh-healthcheck.timer
systemctl list-timers mahdieh-healthcheck.timer      # اجرای بعدی کِی است؟
journalctl -u mahdieh-healthcheck -n 50 -o cat        # نتیجهٔ اجراهای پیشین
systemctl --failed | grep mahdieh                     # آیا وضعیتی جاری قرمز است؟
```

هر اجرای ناموفق، واحد را در حالت `failed` می‌گذارد؛ یعنی `systemctl --failed`
به‌تنهایی فهرست حوادث باز را نشان می‌دهد — بدون هیچ ابزار پایش بیرونی.

## ۴) پایش بیرونی (اختیاری، ولی توصیه‌شده)

پایش درون‌سروری نقطهٔ کور دارد: اگر خودِ سرور برود، هیچ‌کس خبردار نمی‌شود. یک
پایشگر **بیرونی** روی `https://mahdie-shohada.ir/health/live/` بگذارید
(بازهٔ ۱ دقیقه، هشدار پس از ۲ شکست پیاپی). انتخاب ابزار آزاد است؛ شرط قرارداد:

1. فقط نقطهٔ پایانی **زنده‌بودن** را بزند (سبک، بی‌احراز هویت).
2. روی `‎/health/ready/` هشدار بگذارد فقط اگر کد ۵۰۳ دید (افت‌کرده = ۲۰۰).
3. در صفحهٔ پایش، `status` و `degraded` را با هم ببیند، نه فقط کد وضعیت.

## ۵) آزمون آژیر (هر فصل یک بار انجام دهید)

پایشِ آزمایش‌نشده یعنی پایش ناموجود. روی سرور پیش‌تولید:

```bash
# ۱) آژیر را بشنوید: جدول کش را موقتاً کنار بگذارید ⇒ باید کد ۱ بگیرید
sudo mariadb mahdieh -e 'RENAME TABLE django_cache TO django_cache_off'
python manage.py healthcheck --base-url http://127.0.0.1:8000 --behind-proxy --json
# انتظار: {"status": "degraded", ...} و کد خروج ۱ و یک ایمیل

# ۲) اسپم نبودن را ببینید: همان فرمان را دوباره بزنید
python manage.py healthcheck --base-url http://127.0.0.1:8000 --behind-proxy --notify
# انتظار: **هیچ ایمیل تازه‌ای نیاید**

# ۳) خبر خوب را بشنوید: جدول کش را برگردانید
sudo mariadb mahdieh -e 'RENAME TABLE django_cache_off TO django_cache'
python manage.py healthcheck --base-url http://127.0.0.1:8000 --behind-proxy --notify
# انتظار: کد خروج ۰ و یک ایمیل «بازگشت به وضعیت سالم»
```

اگر هر سه مرحله همان‌طور که نوشته شده رفتار نکرد، پایشگر قابل اعتماد نیست و
باید **پیش از** حادثهٔ واقعی رفع شود.
