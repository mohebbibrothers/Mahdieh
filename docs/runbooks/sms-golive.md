# رانبوک «روز راه‌اندازی پیامک» — کدها که از پنل رسید

> مخاطب: مهندس عملیات. این سند برای **یک روز مشخص** نوشته شده: روزی که دامنه
> بالا آمده، پنل الگوها را تأیید کرده و ۱۱ کد الگو برایتان فرستاده است. آن روز،
> این سند را گام‌به‌گام اجرا کنید؛ چیزی از حفظ انجام ندهید.

---

## ۰) چرا این روز، پرریسک‌ترین روز پروژه است؟

پنل ایران‌پیامک الگو را **تنها پس از بالا آمدن دامنه** تأیید می‌کند؛ پس همهٔ
کدها یک‌جا می‌رسند: ۱۱ کد (۹ الگوی زائر + ۲ درونی). سه ریسک واقعی:

۱. **کد جا افتاده**: یکی از کدها تایپ نشده و رزرو آن زائر بی‌پیامک می‌ماند.
۲. **کد غلط**: یک نویسه اشتباه ⇒ پنل خطا می‌دهد یا (بدتر) پیام نامرتبط می‌فرستد.
۳. **سکوت**: کسی نمی‌فهمد کدام الگو فعال شده و کدام نه.

مسیر زیر این سه ریسک را حذف می‌کند. **هیچ مرحله‌ای را رد نکنید.**

---

## ۰.۵) دروازهٔ انتشار: «آیا این سرور، آمادهٔ زائر است؟»

پیش از هر چیز، دروازهٔ تولید را بزنید (فقط می‌خواند، چیزی تغییر نمی‌دهد):

```bash
python src/manage.py production_check            # خطاهای بلوکه را نشان می‌دهد
python src/manage.py production_check --strict   # سخت‌گیرانه: هشدارهای عمدی هم بلوکه‌اند
```

دو ستون خروجی را بشناسید:

| سبد | معنا | نمونه |
|---|---|---|
| **بلوکه** | تا رفع نشود، انتشار ممنوع | `mahdieh.E004` (ناسازگاری نام محیط)، `security.W018` (DEBUG روشن) |
| **هشدار عمدی، غیربلوکه** | دیده می‌شود ولی سایت را قفل نمی‌کند | `mahdieh.W001` (شمارهٔ پذیرش نرسیده)، `mahdieh.W010/W011` (الگوهای پنل) |

منطق این تفکیک: اگر این دو هشدار بلوکه‌کننده بودند، سایت هرگز بالا نمی‌آمد تا
*خودش* را فعال کند. ولی در **روز انتشار واقعی**، با `--strict` اجرا کنید و هر دو
را هم ببندید — آن روز هیچ استثنایی نمی‌پذیریم.

## ۱) پیش از شروع (۵ دقیقه)

```bash
cd /srv/mahdieh
sudo scripts/preflight_production.sh            # ۱۸ بند بازرسی سرور (نقشهٔ کامل ایرادها)
sudo scripts/preflight_production.sh --with-dast  # و کاوش امنیتی روی همان سرور
sudo systemctl status mahdieh --no-pager        # سرویس سالم؟
curl -fsS http://127.0.0.1:8000/health/ready/    # وابستگی‌ها سالم؟
python src/manage.py sms_patterns                # عکس وضعیت فعلی: همه بی‌کد
```

انتظار درست: در گزارش بالا، **هیچ** الگویی «آماده» نیست و سه قالب حیاتی
(`otp_login`، `booking_confirmed`، `offer_created`) قرمزند. این یعنی سامانه
صادق است، نه خراب.

## ۲) ثبت محتوای الگوها در پنل

متن کامل هر الگو (خط‌به‌خط، آمادهٔ کپی) در `docs/sms/pattern-request.md`
است. هر الگو را عیناً همان‌طور ثبت کنید؛ **متغیرها را با نام لاتین کوچک**
بنویسید (`{name}`، `{rooz}`، `{unit}`، `{window}`، `{link}`، `{code}`،
`{date}`، `{position}`، `{offers}`، `{message}`).

> اگر پنل متغیر را با نام دیگری می‌پذیرد، **نام پنل را به ما بگویید**؛ نگاشت در
> `apps/notifications/patterns.py` یک خط است، ولی متن الگو را خودسرانه عوض
> نکنید — آزمون‌ها هم‌خوانی متن و نگاشت را می‌سنجند.

## ۳) فعال‌سازی با یک فرمان (بی‌ریسک)

فایل کدها را بسازید (هر خط یک کد):

```bash
sudo tee /root/mahdieh-sms-codes.txt >/dev/null <<'CODES'
otp_login=کددریافتی
welcome=کددریافتی
booking_confirmed=کددریافتی
booking_reminder=کددریافتی
booking_cancelled=کددریافتی
booking_moved=کددریافتی
offer_created=کددریافتی
offer_accepted=کددریافتی
waitlist_joined=کددریافتی
waitlist_requeued=کددریافتی
feedback_request=کددریافتی
staff_alert=کددریافتی          # اختیاری
dry_run=کددریافتی             # اختیاری — برای آزمون روز راه‌اندازی
CODES
sudo chmod 600 /root/mahdieh-sms-codes.txt
```

**نخست بازرسی (هیچ تغییری اعمال نمی‌شود):**

```bash
sudo scripts/sms_golive.sh --codes-file /root/mahdieh-sms-codes.txt --check
```

اگر خطای «کدهای حیاتی غایب» دید، یعنی یکی از سه کد مهم نیامده — همان را از پنل
بگیرید. اگر عمداً ناقص می‌خواهید فعال کنید (مثلاً `offer_created` را بعداً
می‌گیرید)، `--allow-missing` بدهید؛ سامانه در آن حالت **پیام‌های آن الگو را
مسدود می‌کند** (پیام ناقص هرگز نمی‌رود) و بقیه کار می‌کنند.

**سپس اعمال، ری‌استارت و آزمون واقعی:**

```bash
sudo scripts/sms_golive.sh \
  --codes-file /root/mahdieh-sms-codes.txt \
  --to 0912XXXXXXX \
  --restart --selftest
```

این فرمان: پشتیبان می‌گیرد ⇒ کدها را در `/etc/mahdieh/mahdieh.env` می‌نویسد
(دسترسی ۶۰۰) ⇒ سرویس را ری‌استارت می‌کند ⇒ سلامت را می‌سنجد ⇒ `sms_patterns --check`
را اجرا می‌کند ⇒ **یک پیام واقعی** به شمارهٔ شما می‌فرستد.

## ۴) اگر چیزی خراب شد

```bash
sudo scripts/sms_golive.sh --rollback --restart   # بازگشت به فایل محیط پیشین
sudo journalctl -u mahdieh -n 100 --no-pager | grep -i sms
```

`--rollback` آخرین پشتیبان را برمی‌گرداند و سرویس را بالا می‌آورد. هیچ‌وقت
فایل محیط را دستی با `vi` بازنویسی نکنید؛ همان یک فرمان، اتمی و برگشت‌پذیر است.

## ۵) تأیید پایانی (شاهدِ مکتوب)

```bash
python src/manage.py sms_patterns              # باید همهٔ حیاتی‌ها ✓ باشند
python src/manage.py sms_patterns --json | head -20
python src/manage.py sms_selfcheck             # بازرسی بی‌شبکه
```

و یک آزمون واقعی از مسیر کاربر (نه دستور):

۱. با شمارهٔ خودتان در `/login/` وارد شوید ⇒ پیامک کد ورود باید برسد.
۲. در `/my/` یک سانس رزرو کنید ⇒ پیامک تأیید رزرو باید برسد.
۳. اگر صف انتظار دارید: یک نفر را در صف بگذارید، رزرو را لغو کنید ⇒ پیامک
   پیشنهاد سانس باید برسد (این همان `offer_created` است).

هر سه مورد را با زمان انجام در دفتر عملیات ثبت کنید. «آزمون شد» بدون تاریخ و
شمارهٔ پیام، شاهد نیست.

## ۶) پس از فعال‌سازی: سیاست‌ها را با ترافیک واقعی تنظیم کنید

| کلید سیاست | پیش‌فرض | چرا ممکن است عوض شود |
|---|---|---|
| `waitlist.offer_window_minutes` | ۳۰ | اگر نرخ پذیرش پیشنهادها پایین بود، بیشترش کنید |
| `notification.reminder_lead_hours` | ۲۴ | یادآور پیش از پذیرش؛ با ساعت سفر زائران تنظیم کنید |
| `rate_limit.*` | پیش‌فرض | مبدأهای مشترک (NAT) ممکن است سقف بالاتری بخواهند |

تنظیم از پنل سیاست `/board/policies/` انجام می‌شود (با ثبت نسخه و حسابرسی)، نه
با ویرایش کد.

## پیوست: نگاشت قالب ↔ متغیرها

هر الگو فقط همان متغیرهایی را می‌پذیرد که در `docs/sms/pattern-request.md`
آمده است. اگر پنل متغیر بیشتری بخواهد، ارسال **مسدود** می‌شود و در گزارش
`sms_patterns --json` دیده می‌شود؛ این عمدی است: پیام با جای‌خالی پرنشده هرگز
برای زائر نمی‌رود. جزئیات فنی: `apps/notifications/patterns.py`.
