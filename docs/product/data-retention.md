# نگهداری داده و کمینه‌سازی هویت زائر

«هر داده‌ای که برای ارائهٔ خدمت لازم نیست، نگه‌داشتنش فقط ریسک است.» این سند
می‌گوید چه چیزی، چه وقت و چرا پاک می‌شود — و چه چیزی **عمداً** می‌ماند.

## چرا هر دو کار را می‌کنیم؟

| کار | چرا |
| --- | --- |
| **کمینه‌سازی** (نه حذف کامل) | تاریخ اقامت‌ها مبنای آمار ظرفیت و جلوگیری از سوءاستفاده است؛ پاک‌کردن کامل، آمار زائرسرا را نابود می‌کند. |
| **ماندن شمارهٔ تلفن** | شماره، شناسهٔ ورود زائر است. اگر پاک شود، زائر قدیمی دیگر نمی‌تواند برگردد. |
| **حذف کامل به‌درخواست** | اگر خودِ زائر بخواهد، مسیر جدا وجود دارد (پایین‌تر، «حق پاک‌کردن»). |

## چه چیزی پاک می‌شود و چه چیزی می‌ماند

| داده | سرنوشت |
| --- | --- |
| نام و نام خانوادگی | ⇒ «زائر» (جانشین ثابت، تا رابط کاربری جاهای خالی نشان ندهد) |
| شهر و استان | پاک |
| کد ملی (رمزنگاری‌شده) و ایندکس کور | پاک — جست‌وجو با کد ملی دیگر ممکن نیست |
| ایمیل، آخرین آی‌پی ورود | پاک |
| **شمارهٔ تلفن** | **می‌ماند** (شناسهٔ ورود) |
| تاریخ و سانس اقامت‌ها | **می‌ماند** (آمار و جلوگیری از تکرار) |
| رکورد حسابرسی | **می‌ماند** (زنجیرهٔ حسابرسی نباید سوراخ شود) |

## پنجره‌ها (سیاست، نه کد)

مدیر می‌تواند این‌ها را از پنل تغییر دهد؛ هر تغییر یک `PolicyRevision` با دلیل
می‌سازد.

| کلید سیاست | پیش‌فرض | معنا |
| --- | --- | --- |
| `data.guest_retention_days` | ۱۰۹۵ روز (۳ سال) | بی‌فعالیتی بیشتر از این ⇒ کمینه‌سازی |
| `data.sms_ledger_retention_days` | ۱۸۰ روز | عمر دفتر پیامک (ردیف‌های کهنه پاک) |
| `data.idempotency_retention_days` | ۳۰ روز | عمر کلیدهای هم‌توانی |

## شرط‌های کمینه‌سازی (همه باید برقرار باشد)

1. نقش، «زائر» است — کارکنان هرگز.
2. **رزرو فعال ندارد** (اقامت جاری یا آینده) — مهمانِ امروز دست‌نخورده است.
3. آخرین فعالیت (آخرین ورود، آخرین ثبت، آخرین اقامت) پیش از مرز نگهداری است.

## اجرا

```bash
make retention ARGS="--stats"      # فقط آمار: چند نفر واجد شرط‌اند؟
make retention ARGS="--dry-run"    # فهرست دقیق بدون هیچ تغییری
make retention                     # اجرای واقعی
```

در تولید با تایمر هفتگی اجرا می‌شود: `mahdieh-retention.timer` (بامداد یک‌شنبه،
۰۴:۳۰). هر اجرا در زنجیرهٔ حسابرسی کنش `data.guest_redacted` را ثبت می‌کند و
اجرای دوباره بی‌اثر است (idempotent).

## حق پاک‌کردن (درخواست خود زائر)

اگر زائر بخواهد داده‌اش پاک شود، بک‌اند مسیر جدا دارد:
`apps.identity.retention.erase_guest_data` — **دلیل اجباری** است و در حسابرسی ثبت
می‌شود؛ پنجرهٔ نگهداری را هم دور می‌زند (فوراً اجرا می‌شود). روند پذیرش درخواست و
پاسخ به زائر در رانبوک `docs/runbooks/guest-support.md` آمده است.

## چه چیزی هنوز باز است

- **حذف کامل حساب** (حذف ردیف کاربر): فعلاً فقط برای خطای ثبت و بنا به تأیید مدیر
  انجام می‌شود، چون رزروها به کاربر `PROTECT` هستند. اگر لازم شد، مسیر
  «ناشناس‌سازی + ابطال دسترسی» (غیرفعال‌کردن ورود) اضافه می‌شود.
- **دفتر حسابرسی**: عمداً حذف نمی‌شود (زنجیره یکپارچه باید بماند). اگر سیاست
  نگهداری برای آن لازم شد، باید با «بایگانی سرد + لنگر» انجام شود، نه حذف ساده.
